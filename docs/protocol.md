## 2. Features

- **Causal user-day features:** counts per canonical action, plus deviation from the same user's strictly earlier days. No future information.
- **Shared schema (C2 variant a):** every client emits the same vector; actions a client never observes are zero-filled, with a per-action missing flag.
- **Client-specific input (C2 variant b):** each client has its own input layer over the actions it observes, feeding a shared encoder.
- **Sequence input (GRU):** the last **k = 7** user-days of the same user (zero-padded at the start of a user's history).

## 3. Splits (fixed rules; same as IJACSA where possible)

| Client | Split type | Rule |
|---|---|---|
| C1 CERT r4.2, C2 CERT r5.2, C3 SPEDIA | **Chronological** | Earliest 70% of the client's timeline = training; latest 30% = test (the IJACSA rule). The last 15% of the training window = validation. The cut is taken at a day boundary |
| C4 LANL | **User-disjoint** | 70% of users = training, 30% = test, stratified by whether a user has any positive user-day (the IJACSA rule). 15% of training users, stratified the same way = validation |

- **Why LANL differs:** in IJACSA the chronological LANL split left *no positive user-days* in the test period, because red-team activity falls early in the 58 days. LANL is therefore scored on unseen users, not later days. This mixed protocol is stated in the paper's threats to validity, and LANL results are not pooled with the other clients' in any average without a note.
- **SPEDIA:** the user-day cache spans 25 days (6–30 March 2025): 17 training, 2 validation and 6 test days. Its ≈ 32% prevalence keeps positives in every partition.
- **Chronological leakage boundary:** a test day may use the same user's earlier training-period days for its causal features (as in IJACSA), never later days.
- **Required check:** each client's validation and test partitions must each hold at least one positive user-day. If one fails, record it in the change log and report the client as not evaluable for that regime. Do not move the cut.

## 4. Leakage controls

1. Scalers, class weights and thresholds are fitted on each client's own training data (thresholds on its validation data).
2. Resampling, if used, is applied to training data only, after the split.
3. No raw data or test statistics leave a client. Federated normalisation, if used, aggregates training-set statistics only.
4. Model selection and early stopping use validation data only. The test period is scored once per frozen configuration.

## 6. Training regimes

| Code | Regime | Notes |
|---|---|---|
| R0 | Local-only | Each client alone |
| R1 | Pooled | All clients' training data together; reference only, not privacy-preserving |
| R2 | FedAvg | Report both size-weighted and equal weighting |
| R3 | FedProx | μ chosen on validation from {0.001, 0.01, 0.1} |
| R4 | Personalised | FedPer-style local head; also FedAvg + local fine-tuning |
| R5 | Zero-shot | Taken from IJACSA (single-source model tested on another client) |
| R6 | Leave-one-client-out FL | Federate three clients, test on the fourth, no fine-tuning (C4) |
| R7 | Similarity-based partner selection | Each client federates only with partners above a similarity threshold chosen on validation (C3) |

**Federations:** {C1,C2} (control), {C1,C3}, {C2,C3}, {C3,C4}, {C1,C4}, {C1,C2,C3}, {C1,C2,C3,C4}, and all four leave-one-out triples.

**FL settings (frozen):**
- Communication rounds T = 100, with the reported model chosen by best mean validation PR-AUC across rounds
- Local epochs E = 1
- Every client takes part in every round
- Optimiser: Adam, learning rate 1e-3, batch size 256
- Class-weighted binary cross-entropy, with weights from each client's own training prevalence
- FedProx μ ∈ {0.001, 0.01, 0.1}, chosen once on validation
- Seeds: 5 (0–4) — extended to 20 (0–19) on 2026-10-14, see change log (j)

Local-only (R0) and pooled (R1) MLP/GRU use the same architecture, trained for 100 epochs with early stopping on validation PR-AUC.

**Framework:** Flower (simulation mode). Sanity check: FedAvg with a single client must reproduce R0 within seed noise.

## 7. Metrics and statistics

- **Primary:** PR-AUC on each client's own test period, plus base-rate lift (PR-AUC ÷ prevalence).
- **Secondary:**
  - recall at a fixed alert budget (top 1% of user-days)
  - precision, recall and F1 at the client's validation-chosen threshold
  - ROC-AUC (reported, not primary)
- **Across clients:**
  - worst-client PR-AUC
  - best–worst gap
  - **negative transfer:** a federated regime's PR-AUC falls below R0 for that client and the 95% CI of the difference excludes 0
- **Cost:** rounds to convergence, bytes sent per round, wall-clock training time.
- **Statistics:** 5 seeds; paired seed-level bootstrap 95% CIs for each regime minus R0, per client; no pooled significance claims across clients.

## 8. C3 similarity measures (computed before any training, from training data only)

| Measure | Definition |
|---|---|
| Prevalence ratio | max(p_i, p_j) / min(p_i, p_j) |
| Action-mix distance | Jensen–Shannon distance between the clients' canonical-action frequency distributions |
| Log-coverage overlap | Jaccard index of observed canonical actions |

**Test:** Spearman correlation between each similarity measure and the observed per-client gain (federated minus R0 PR-AUC), across all client–federation pairs; report with a bootstrap CI.

## 9. Go / no-go and ablations

- **Go/no-go after R0 and R1:** if R1 does not beat R0 for any client, write the paper as a negative result about collaboration across these datasets.
- **Ablation E8:** prevalence-matched SPEDIA (subsample positives to CERT-like prevalence), to separate prevalence effects from label-meaning effects in any negative transfer.
- **Extension, not a contribution:** one label-flipping client with median / trimmed-mean aggregation.
